# Verified obligation execution boundary

This post-closure refactor extracts `VerifiedObligationExecutor` as the composition seam for execution mechanics already shared by onboarding, offboarding, and bounded financial transactions.

## Ownership

`VerifiedObligationExecutor` owns only the generic post-authorization lifecycle:

- execution / reconciliation / verification state progression;
- dispatch of already-planned effects through the configured provider;
- fail-closed handling of ambiguous or unavailable read-back;
- realization evidence creation;
- exact effect-to-confirmed-outcome recording;
- collection of current outcomes and realizations before domain completion assessment.

It does **not** own domain interpretation. Planning, qualification, effect ordering and payload dependencies, semantic reality verification, completion meaning, reopen policy, effective-time rules, transfer semantics, and financial transaction semantics remain on the existing execution engines as hooks.

`OnboardingExecutionEngine` is now the compatibility facade that owns those hooks and delegates `run`, generic dispatch, and generic verification mechanics to one `VerifiedObligationExecutor` instance. Existing offboarding and financial subclasses continue to reach the same lifecycle through `super()`.

## Compatibility

This change deliberately preserves the historical public class surface:

```text
FinancialExecutionEngine(OnboardingExecutionEngine)
OffboardingExecutionEngine(OnboardingExecutionEngine)
```

The child modules and their public methods remain unchanged. Offboarding still wraps `super().run()` with effective-time qualification, preserves its explicit effect ordering, extends verification with continuity transfer fulfillment, and owns transfer-specific completion blocking. Financial execution still validates the financial case kind before delegating through `super().run()`.

Financial qualification waiting remains interpreted by `OnboardingExecutionEngine._require_financial_qualifications` / `FinancialQualificationPending`; the generic executor does not import or interpret financial qualification semantics. Offboarding effective-time qualification, Administrative domain-state fulfillment, continuity transfer, and transfer-specific reopen behavior remain interpreted by `OffboardingExecutionEngine`.

## Invariants

- no schema or migration changes;
- no capability or Agent Kernel contract changes;
- no provider retry-policy changes;
- `OUTCOME_UNKNOWN` still requires reconciliation and never grants blind retry permission;
- provider success still does not substitute for verified reality;
- exact effect / realization / confirmed-outcome lineage is unchanged;
- obligation completion semantics remain domain-owned;
- authority-epoch and governance revalidation remain unchanged;
- stable effect/outcome/evidence identities remain generated by the existing domain facade;
- M5/M7/M8 accepted behavior and evidence are not rewritten.

Simplifying the historical inheritance hierarchy is explicitly out of scope. The purpose of this change is to move the proven generic lifecycle behind a composition seam without changing domain ownership or external execution-engine APIs.
