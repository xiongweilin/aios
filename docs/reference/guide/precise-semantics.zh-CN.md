# 精确语义

> **迁移设计参考（非当前实施规范）**：本文由 [guide/engineering/precise-semantics.zh-CN.md](https://github.com/xiongweilin/guide/blob/511c073322c6b38ed2d36b32492836abf4d69b58/engineering/precise-semantics.zh-CN.md) 迁入，以保存原有工程分析。当前行为、权限、状态、契约和实现以 AIOS 现行 `docs/`、`contracts/`、源码与测试为准。概念框架以 [guide](https://github.com/xiongweilin/guide) 为准；本文不反向定义框架或现实本体。

[English](./precise-semantics.md) | [简体中文](./precise-semantics.zh-CN.md)

> 定位：把“现实—目的性有限行动者—当前边界—充分性—探索/决策—现实反馈”转成可实现、可验证且不允许静默替代的工程语义。

工程目标不是把六维实现成六个字段、六张表、六个服务，也不是建立一个总控式 `sufficient=true`。六维描述当前边界；认识状态横切当前表示；充分性控制具体转换；探索和决策是活动；行动链负责把决定连接到现实并回流反馈。

一个语义区分也不自动要求独立 class、durable entity、表或 service。只有独立 identity、lifecycle、authority、concurrency、provenance、recovery 或 retention 真正重要时才拆分实现对象。

## 0. 工程总链

```text
现实侧输入 / 触发
→ 区分与当前边界
→ 充分性检查
→ 探索或决策
→ 治理依据 / 授权
→ 执行
→ 现实效果
→ 观察
→ 验证
→ 结果 / 义务完成
→ 重新验证 / 恢复 / 重新打开
```

这个链条不是单向流水线；任何现实反馈都可以要求回到更早位置。

## 1. 现实不是数据库字段

- 现实不是等待完整序列化的对象。
- 可区分范围由来源、传感器、API、语言、工具、权限和能力限制。
- 已区分范围是系统当前实际形成并可调用的表示。
- 模式、枚举、标签、本体和策略类别都可能只是默认区分。
- 新工具、权限、关系或接口会改变后续可区分范围。

当开放式请求、任务重构或自主触发会改变目标、范围、权限、不可逆性或完成语义时，至少保留：

```text
边界上下文
- 目的 / 范围
- 当前区分
- 关键关系
- 因果假设
- 时间尺度 / 有效期
- 可能性 / 候选空间
- 价值 / 硬约束
- 默认假设
- 未知
- 来源 / 版本
```

固定且已经充分验证的机器契约可以避免重复持久化完整上下文，但不能跳过真正改变语义边界的检查。

## 2. 六维在工程中的最小责任

| 维度 | 工程上至少保存 |
| --- | --- |
| 区分 | 对象、字段、类别、范围、问题框定及其版本 |
| 关系 | 依赖、角色、权限、所有、组成、网络与参与者关系 |
| 因果 | 干预假设、效果路径、依赖、故障与恢复机制 |
| 时序 | 顺序、有效期、历史、延迟、窗口、路径依赖与重开条件 |
| 可能性 | 候选、未知、可达性、排除依据、恢复和替代路径 |
| 价值 | 目标、硬约束、权利、承诺、风险与规范冲突 |

这不要求物理一一拆分，只要求非法替代无法静默通过。

## 3. 认识状态与来源

外部输入至少区分：

`原始输入 → 表示 → 主张 → 有支持 / 权威事实`

最小事实主张：

```text
事实主张
- key / value
- source
- source_ref
- source_version
- observed_at
- provenance
- authority: claimed | derived | authoritative
- epistemic_status:
  unverified | supported | disputed | refuted | unknown | needs_revalidation
```

模型提取、用户输入、缓存、搜索索引和同步副本默认都不是权威事实。

`记录存在 ≠ 内容为真`

`模型高置信度 ≠ 来源权威性`

当前资格也不应被当成一条永久写死的历史字段。一个结论如果依赖其他前提，那么这些前提一旦失去当前资格，失效应沿依赖关系传递到结论；相反，与失效链无关、仍有独立现实依据的证据可以继续有效。历史记录保留不变，当前资格根据依赖关系重新判断。

## 4. 充分性机制必须保存

最终“足够”不能脱离它怎样成立。

### 解释型

```text
解释型充分性
- target_transition
- boundary_version
- scope / purpose / timescale
- evidence / counterevidence
- assumptions / default distinctions
- competing explanations
- residual_unknowns / accepted_risks
- rationale
- accountable_judger
- disposition
- reopen_conditions
```

### 规定型

```text
规定型充分性规则
- rule_id / version
- authority_source
- applicability
- valid_from / valid_until
- required_inputs
- predicate / threshold / guards
- exceptions

规定型评估
- rule_ref
- input_versions
- result
- unmet_conditions
- evaluator
- evaluated_at
```

`解释判断 ≠ 规定规则评估`

`规则评估为真 ≠ 规则适用 / 当前有效 / 有权限`

规则适用性存在实质含糊时，应先进入解释型充分性。反复解释若要变成机器规则，必须显式规则制定、版本化和权限来源。

充分性是一项工程责任，不要求存在统一 universal payload。具体系统可以通过 owner-local qualification / admission、显式依据引用、守卫条件、ReviewCase 和领域 acceptance contract 来实现。只要这些机制能够保存“为什么当前转换现在被允许”的依据，就不需要引入单一跨领域 `Sufficiency` 对象。

## 5. 禁止语义捷径

| 已成立 | 不能自动推出 |
| --- | --- |
| 收到请求 | 问题框定已经充分 |
| 模式中有分类 | 这是现实唯一边界 |
| 收到数据 | 内容为真 |
| 模型高置信 | 权威事实 |
| 事实可用 | 规则已满足 |
| 规则满足 | 决定有效 |
| 决定有效 | 已授权 |
| 已授权 | 已执行 |
| 提供方成功 | 现实效果发生 |
| 现实效果发生 | 后置条件验证通过 |
| 验证通过 | 全部义务完成 |
| 事项完成 | 长期责任解除 |
| 历史有效 | 当前仍有效 |

跨越两个以上边界的单一字段应被视为语义压平风险。

## 6. 身份、角色、委派与授权

身份认证只回答“这是谁”。

授权至少绑定：

```text
授权
- principal
- operation
- resource / subject
- scope
- authority_source
- delegation_ref
- issued_at
- expires_at / revocation_version
```

角色、职位、历史分配或业务决定不能自动变成当前资源权限。

`定义权 ≠ 判断权 ≠ 决定权 ≠ 执行权限`

## 7. 规则定义、评估与决定

```text
规则版本
- policy_id
- version
- owner
- effective_range
- definition_summary

规则评估
- policy_version
- input_versions
- result
- rationale / unmet_conditions
- evaluated_at

决定
- decision_id
- subject
- scope
- purpose
- decision_maker
- authority_basis
- boundary_version
- policy_version
- input_versions
- disposition
- created_at
```

决定必须绑定当时支持它的输入、边界和规则。

旧标识仍存在，不表示当前仍可使用。

规则“适用”“已激活”和“允许某主体执行具体操作”也必须分开。

## 8. 治理依据

高影响决定或权限授予应保存可重建依据：

```text
治理依据
- subject / case
- boundary_version
- fact_dependencies
- relation_dependencies
- causal_assumptions
- temporal_validity
- possibility_constraints
- value_constraints
- policy_versions
- required_approvals
- authority_refs
- residual_unknowns
- expected_self_changes
- reopen_conditions
- created_at
```

它的用途是重建当时为什么成立，并判断现在是否仍成立。

执行本身预期会改变的字段，不应被错误当作“执行后使依据失效”的前置依赖；真正前置依赖变化则必须触发重新验证。

## 9. 状态与转换

重要转换至少检查：

```text
current_state
+ trigger
+ expected_version
+ preconditions
+ sufficiency_basis
+ current_authorization
+ decision / governance_basis
+ temporal_validity
+ allowed_side_effects
→ next_state
```

合法终点不能证明路径合法。

并发更新应使用版本、ETag、CAS、乐观锁或等效机制。冲突时重新读取当前状态，而不是让后写覆盖擦掉语义冲突。

## 10. 范围与副作用

操作应声明：

- 可以改变什么；
- 不可以改变什么；
- 允许哪些副作用；
- 目标后置条件；
- 关键不变条件。

执行后既验证目标字段，也验证重要的“不应变化”。

扩大对象集合、权限、范围或副作用类型，应进入新的充分性 / 决策 / 授权路径。

## 11. 时效有效性

当前依据可能因以下变化失效：

- 来源或来源版本；
- 规则版本；
- 角色、委派或权限；
- 范围、分区或分配；
- 模型、数据、代码、工具；
- 依赖、环境、资源；
- 未解决复核；
- 关键假设；
- 价值或权利条件。

`记录很新 ≠ 依赖仍然有效`

时效判断应检查来源、依赖和当前任务，而不只看时间戳。

“陈旧”也不是对所有事实一刀切的属性。某条信息虽然较旧，只要当前任务所需的区别在它所覆盖的范围内没有变化，它仍可能足以支持这个任务；反过来，看起来很新的信息如果漏掉了任务所需的关键区别，也可能不足。明确到期的规则、授权和时限约束仍应按其有效期严格处理。

## 12. 复核、重新验证、重新打开与重新授权

- **复核义务**：发生了足以要求重新检查的变化；
- **重新验证**：判断旧事实、决定、依据或权限是否仍适用；
- **重新打开**：恢复事实取得、候选生成或治理过程；
- **重新授权**：重新取得执行权限。

依赖变化通常先产生复核义务，不应自动改写历史，也不应自动生成新决定。

`重新打开 ≠ 自动获得授权`

跨版本迁移还需要额外检查。新版本能够读取旧记录，只说明格式可读；它不能证明旧判断在新规则、新评估器或新语义下仍然成立。旧结论只有在存在明确的保持依据时才应继续取得当前资格，例如能说明新版本保持了相关判断，并且没有改变该判断所依赖的外部目标或约束。没有这样的依据，就应保留历史，但把相关结论放回复核或重新验证。

## 13. 幂等与外部效果

相同幂等键可以防止请求重复处理，但不能证明外部副作用安全重复。

```text
执行尝试
- request_id
- decision_ref / authorization_ref
- subject / resource
- operation
- idempotency_key
- expected_postconditions
- provider_ref
- started_at / ended_at
- transport_result
```

支付、消息、账户创建、权限授予等操作超时后可能已经发生。

`传输幂等 ≠ 效果幂等`

含糊结果应进入校正，不默认失败，也不默认重试。

## 14. 本地事务与外部一致性

数据库事务只能保证本地原子性，不能让数据库和外部现实共同原子提交。

可按业务选择 transactional outbox、inbox/dedup、saga、补偿、持久工作流或校正进程。

无论实现方式如何，都必须表示部分成功与未知效果。

## 15. 观察现实

```text
观察
- authoritative_source
- subject_identity
- source_version
- observed_at
- availability
- freshness
- existence
- state
```

至少允许：

`存在 | 缺失 | 不可用 | 未知`

`当前有效 | 过期 | 未知`

来源不可用不等于对象缺失。

## 16. 验证后置条件

```text
验证
- execution / effect_ref
- expected_postconditions
- observation_ref
- disposition:
  verified | missing | inconsistent | unavailable | stale | unknown
- diff
- verifier
- verified_at
```

验证应读合适现实来源，并检查身份、目标状态、范围和意外副作用。

执行器自己的成功输出不能代替现实验证。

## 17. 效果溯源连续

如果系统主张“这个操作产生这个结果”，应能追踪：

`触发 → 边界 → 充分性 → 决定 → 授权 → 执行 → 观察 → 验证 → 结果`

终点正确不足以证明因果链正确。

## 18. 义务独立于规划器

执行规划器不应自己定义业务完成语义。

```text
义务
- obligation_id
- subject
- required_state / action
- authority_class
- required
- source_policy / decision

完成评估
- obligation_set_ref
- covered_effects
- verified_results
- missing_obligations
- residual_obligations
- satisfied
```

`已验证效果 ≠ 事项完成`

`事项完成 ≠ 责任解除`

## 19. 类型、认识状态与生命周期正交

不要把 record type、epistemic status 和 lifecycle 压成一个枚举。

记录可以承担边界上下文、问题候选、证据、观察、主张、推导、目标、约束、实验、决定、行动、规则、结果、修订等语义角色。

现在不可使用，不表示应删除历史。

## 20. 审计不改写历史

高影响链路应使用只追加记录或等效可追踪设计。

撤销、回滚、补偿和重开创建新记录，不删除旧记录。

系统应能回答：谁在什么边界、输入和规则下决定；谁授权；执行了什么；现实后来怎样；如何验证；为什么又发生变化。

## 21. 语义入口是信任边界

模型、外部服务、用户或其他系统的内容进入权威语义前，必须按来源类型验证。

任何扩大权限、清除阻塞或创建现实副作用的正向转换，在来源、范围、权限、时效或溯源缺失时应默认停止。

默认停止只表示“现在不能继续”，不能伪造相反事实。

当检查器、评估器或规则系统能够修改并批准自己的后继版本时，自身批准不能单独证明后继版本在语义上仍然可靠。工程上至少要保留一个非循环的可信起点，或者保存可以独立检查的保持依据，说明新的检查器、评估器或规则为什么仍然满足原来依赖的语义约束。

## 22. 责任角色与失败独立

可区分：

- 解析 / 提取；
- 推理 / 候选生成；
- 充分性判断；
- 规则评估；
- 决定；
- 授权；
- 执行；
- 观察；
- 验证；
- 校正 / 恢复；
- 复核 / 重开。

一个进程可以实现多个角色，但契约和记录必须保存角色差别。

`角色分离 ≠ 故障独立`

多个评估者共享同一数据、模型、指标、身份基础、权限来源、技术根或利益结构时，不应被当作独立证据。

## 23. 多版本轴

至少独立考虑：

- 数据 / 记录模式；
- 边界语义；
- 状态机；
- 策略规则；
- 授权契约；
- 运行时协议；
- 模型 / 评估者。

`旧 JSON 仍可解析 ≠ 语义兼容`

升级要检查默认行为、权限、范围、历史解释、评估标准以及重开要求是否变化。只要版本变化会改变“什么算成立”“什么算改进”或“什么证据仍可用”，就应把保持关系作为显式迁移依据，而不是默认继承旧结论。

## 24. 最小可部署契约

产生现实副作用的系统至少需要等效语义：

```text
boundary_context
fact_claim
sufficiency_basis
policy_version / policy_evaluation
decision
governance_basis
authorization
obligation_set
execution_attempt
observation
verification
effect / reconciliation_state
completion_evaluation
review_obligation
audit_record
```

它们不必一一成为独立 durable entity。

## 25. 最小不变量

1. 当前表示不等于现实。
2. 模式缺失不等于现实不可能。
3. 模型输出默认不是权威事实。
4. 解释型与规定型充分性不能互相冒充。
5. 规定规则满足不自动证明适用性、时效、权限或规范有效性。
6. 历史解释不能静默成为确定性规则。
7. 没找到路径不能直接变成“不可能”。
8. 决定不能直接创造底层权限。
9. 执行前检查当前授权与关键依赖版本。
10. 合法终点不能证明转换合法。
11. 扩大范围需要新的充分性与权限。
12. 提供方未知结果不自动成为失败，也不表示安全重试。
13. 已验证结果来自现实回读，不来自执行器自声明。
14. 义务独立于规划器。
15. 修正、回滚和补偿不删除历史。
16. 关键依赖变化进入复核 / 重新验证。
17. 重新验证不自动续权；重新打开不自动授权。
18. 完成不自动等于长期责任解除。
19. 六维不要求一一对应字段、服务或层。
20. 角色分离不自动产生故障独立。
21. 局部充分不自动建立组合整体充分。
22. 竞争框定不需要先翻译成当前框架才有挑战资格。
23. 历史证据被保留，不等于它仍具有当前资格；依赖失效应传递到依赖它的结论。
24. 版本可读取旧数据，不等于旧判断在新语义下仍然成立；需要明确的保持依据。
25. 信息是否过旧，应相对于当前任务和依赖判断；明确到期的规则与授权仍按有效期处理。
26. 自身批准、内部评分或后继版本被当前版本接受，都不能单独证明语义可靠性。

## 26. 最小符合性测试

至少测试：

- 默认类别不能无依据被当作现实唯一边界；
- 重要问题框定不足时不能直接进入决定 / 执行；
- 解释型判断不能被当成规定规则结果；
- 规定规则过期、越界、未授权或适用性不足时不能放行；
- 规则适用性含糊时回到解释型判断；
- 解释结果规则化必须产生新规则和版本；
- 候选空间未充分有界时，没找到路径保持未知而不是不能；
- 工具、权限、关系或接口变化可以重开边界；
- 高置信模型主张不能直接变成权威事实；
- 共享共同故障源的多个评估者不能被算作独立冗余；
- 评估器、规则或模型版本变化时，依赖旧版本的结论不会在没有保持依据的情况下自动继承当前资格；
- 一个检查器认可自己的后继版本，不能单独被当作后继版本语义可靠的证明；
- 局部对象各自充分但组合产生新假设 / 权限 / 反馈时，需要组合层依据；
- 明确过期的规则、决定和权限被拒绝；较旧的事实或证据只有在仍足以支持当前任务、且关键依赖未失效时才能继续使用；
- 操作不能越出授权范围；
- 非法转换即使终点合法也被拒绝；
- 自身预期变更不会错误使治理依据失效；
- 真正前置依赖变化会触发重新验证；
- 超时和确认丢失进入校正而不是盲重试；
- 提供方成功但现实不一致不能确认成功；
- 规划器遗漏义务时完成失败；
- 回滚后历史仍可追踪；
- 存在剩余义务时不能解除长期责任；
- 多个语义位置共享同一记录时，非法替代仍被拒绝。

如果一个理论边界不能改变契约、转换、失败路径或测试，它就不应继续占据工程语义层。

## 27. 工程质量评价

语义不变量与符合性测试约束正确性，但通过这些检查本身不能证明框架的实际使用质量或实现系统的整体质量。具体使用可以按六项与任务相关的指标评价：

| 指标 | 评价问题 |
| --- | --- |
| **正确性** | 区分、判断、行动和最终主张，是否与当前可取得的现实侧证据、预期语义和实际结果相符？ |
| **可用性** | 人和系统是否能够以不过度困难的方式理解、应用、维护和修订这套框架？ |
| **可靠性** | 在重复使用、条件变化、异常和失败下，框架是否仍能稳定提供可依赖的指导，并支持校正或恢复？ |
| **性能** | 使用框架形成决定、协调或工程结果时，其延迟、响应速度和吞吐是否满足当前任务需要？ |
| **容量 / 可扩展性** | 当用户、数据、任务、领域、依赖和互动复杂度增长时，框架是否仍然可用，而不会出现不可接受的退化？ |
| **效率** | 为取得有用结果所消耗的时间、计算、金钱、注意力、协调、维护和机会成本是否相称？ |

这六项是实际使用质量指标，不是额外的理论工作视角、基础公理或通用充分性证明。哪些指标相关、怎样测量、验收阈值与相对权重如何确定，取决于具体任务和运行条件。单项指标表现良好不等于整体充分；现实侧结果出现实质退化时，应复核当前依据，并修订适用的边界或契约。

## 28. 判断与预测验证的条件性接入

当领域将重要预测、形式证明或评估结果用作决定 / 授权 / 执行准入依据时，必须保留能重建对应主张的**条件、来源 / 模型版本、验证方法和当前资格**。经验预测如果要声明质量改善，需有事前锁定的预测、可独立取得的后续结果、固定基线和相称的误差 / 校准比较；缺失结果时保持未知，不虚报命中率。

允许由领域已有对象、证据引用与审计沿革承载这些责任，无需新增统一 Prediction 表、全局评分器或领域通用概率指标。形式模型测试不能替代现实效果回读；提高内部评分不表示外部目标改善；预测准确也不创造决定权或执行权限。

条件性符合性检查：

- 有明确数学条件的主张能复算；已证无解不能被报告为有解，未找到解不得冒充无解证明；
- 重要条件、输入、规则或评估器版本变化时，不经适用性复核不得沿用旧结论；
- 经验预测的验证结果不能从执行器自报成功推导；结果不可观察时保留未知；
- 预测版本之间的改进比较不能事后改换基线、时间窗口、样本总体或损失函数而不披露；
- 已观察结果不自动证明干预因果效应，也不改变现有授权链。

具体方法与有限回归案例见[判断与预测验证协议](https://github.com/xiongweilin/guide/blob/main/framework/judgment-validation.zh-CN.md)和[十个多行动者案例](https://github.com/xiongweilin/guide/blob/main/framework/examples/judgment-prediction-cases.zh-CN.md)。
